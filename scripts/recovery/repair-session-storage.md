# Offline session migration repair

`repair-session-storage.py` repairs session anomalies left by the BitFun to
OpenBitFun migration and subsequent automatic runtime-directory migration. It
repairs local and remote-workspace sessions stored on this host, plus proven stale
assistant workspace IDs and paths. It is
standalone Python 3.8+ and uses only the standard library. Send this file to an
affected user; Node, Rust, OpenBitFun source code, and additional Python packages
are not required.

The script scans `projects/*/sessions` and old `remote_ssh` session directories.
It compares session metadata, session state, and the workspace registry, then
calculates the current hashed runtime directory. Normal local workspaces,
assistant workspaces, registered remote workspaces, and their internal child
sessions are eligible. Metadata-only legacy sessions can be resolved by a unique
registered workspace path (plus SSH host for remote workspaces).

For named assistant workspaces under `.openbitfun/personal_assistant`, it derives
the corresponding `.bitfun` path and old stable ID. Only this exact proven mapping
can rewrite an unknown ID. Existing old/current IDs or inconsistent paths are
never guessed over. Both metadata and state references are repaired where present,
including old assistant paths and execution-target roots. A session already in its
correct directory can receive an identity-only repair. Unknown fields and all
non-identity session data remain intact.

## Windows usage

Run on the machine that owns the data. Use `python --version` to check Python is
available; `python` below can be replaced with the full path to `python.exe`.
The Python launcher (`py -3`) is optional.

Save the script in a convenient folder and open PowerShell there. Create a
read-only plan with a new output filename:

```powershell
python .\repair-session-storage.py --plan "$env:USERPROFILE\Desktop\session-repair-plan.json"
```

Planning, applying, and rolling back display progress automatically on stderr.
Updates show the current stage, completed item count (with a total when known),
current path, and elapsed time. During long operations such as copying a session
backup, the latest status refreshes every two seconds; this indicates that the
process is still running, not a byte-level copy percentage. Output is flushed
immediately, including when redirected to a log. Result summaries stay on stdout.

Inspect the plan's `operations` and `diagnostics`. Each repair records the session
name, source, target, workspace ID/path, lightweight directory fingerprints, required workspace
snapshot files, and `identity_changes` showing every old/new identity field.
`file_updates` stores original and repaired JSON bytes encoded as base64 for exact
verification and rollback. Skipped sessions have explicit reasons. Planning writes
only the requested plan, outside the data roots. It does not repair anything.
Planning while OpenBitFun is running is allowed, but changes made afterward can
make the plan stale; regenerate it after closing the app if applying is refused.
Original and repaired fingerprints share one directory traversal during planning
and plan validation. Planning reuses catalog metadata bytes and parsed documents
for ownership checks and identity updates; index rebuilding also reuses its catalog
metadata instead of reading it again.
Plans generated by older script builds used full-content fingerprints and are not
accepted by this build; generate a new plan before applying.

Close every OpenBitFun Desktop/CLI process that uses these data roots, including
background hosts receiving remote requests. Keep them stopped until the repair
finishes. Then apply the reviewed plan, using a **new** backup directory:

```powershell
python .\repair-session-storage.py --apply --plan "$env:USERPROFILE\Desktop\session-repair-plan.json" --backup-dir "$env:USERPROFILE\Desktop\session-repair-backup" --confirm-closed
```

Windows also checks for running OpenBitFun/BitFun executable names. This check
cannot identify every renamed/custom host; `--confirm-closed` remains the user's
confirmation that all writers are stopped. After a successful repair, reopen
OpenBitFun and check the previously affected sessions.

Defaults match standard OpenBitFun storage:

| Setting | Default |
| --- | --- |
| `--home` | `OPENBITFUN_HOME`, otherwise `~/.openbitfun` |
| `--user-root` | `OPENBITFUN_USER_ROOT`, otherwise the OS config directory's `openbitfun` folder |
| Registry | `<user-root>/data/workspace_data.json` |

On Windows the default config directory is `%APPDATA%`; on macOS it is
`~/Library/Application Support`; on Linux it is `$XDG_CONFIG_HOME` or `~/.config`.
Pass `--home` and `--user-root` explicitly when generating a plan for custom
storage or a different product namespace. The registry must have the current
`format_version: 1` and `product_id: "openbitfun"` format. Apply uses the roots
saved in the plan, not the current environment. Registered local workspace
directories must exist so canonical paths can be calculated reliably.

## What changes

Before modifying product data, the script copies and verifies each complete
session directory and saves original affected `index.json` and search-cache
files in the backup. It then renames whole session directories and applies only
the identity JSON changes shown in the plan. Turns, context snapshots, attachments,
prompt caches, and unrecognized files move together; unknown JSON fields remain.

Workspace file snapshots are separate from session context snapshots. The script
copies operation histories for the session and its `snapshot_session_id`, their
referenced before/after snapshots, references in `session-revert.json`, and content
blobs. Baselines are copied only when explicitly referenced by those records; the
script does not scan the workspace baseline directory. Unreferenced baselines
remain at their original location, so a session moved to another runtime may lose
its workspace-wide baseline comparison until a new baseline is created. Session
file-operation history and its referenced snapshots are preserved.
Inline compressed snapshot content is supported. Original shared snapshot files
remain in place. An identical existing
destination asset is reused; a different one blocks that session's move. Missing
referenced metadata/content also blocks the move.

Remote paths are compared as case-sensitive POSIX paths on every operating system.
Remote runtime keys hash the registered SSH host and remote root; the remote
workspace need not exist locally. Remote file snapshots are copied only from the
verified SSH connection's `snapshots/workspace-identities/<hash>` scope. Unscoped
legacy snapshots cannot prove which SSH profile owns them and remain untouched,
matching the product's policy. Missing scoped references or ambiguous profile
identity are reported rather than reassigned to another connection. Empty legacy
remote directory trees do not produce skipped-session diagnostics.

Affected session indexes are rebuilt from all per-session metadata, retaining
unknown metadata fields and the product's hidden-child rules. Malformed metadata
in an affected directory blocks its repair. The rebuildable
`product-search-v1.sqlite` cache and its WAL/SHM files are backed up and removed
so the product rebuilds search data. Other workspace resources, settings,
memories, and registry records are left in place.

## Interrupted repair and rollback

A durable journal records backups, snapshot copies, index writes, and newly
created directories. If an ordinary error interrupts an apply, keep OpenBitFun
closed and repeat the **same apply command with the same plan and backup**.
Already moved directories are verified rather than overwritten. Repeating a
completed repair verifies it and performs no writes to product data.

If the process was forcibly terminated, `.session-storage-repair.lock` may remain
under the product data root. Confirm that no repair process or OpenBitFun host is
running before manually removing that one lock file. Then repeat the command.
If the backup has no `journal.json`, preparation was interrupted before product
data was modified; retain that incomplete backup and apply using a new backup
directory. Do not edit a plan or journal to bypass validation.

To undo the repair while all hosts remain closed:

```powershell
python .\repair-session-storage.py --rollback "$env:USERPROFILE\Desktop\session-repair-backup" --confirm-closed
```

Rollback verifies sessions, catalogs, copied snapshots, and affected
indexes/caches before moving anything. It refuses if user data changed after the
repair. It restores session locations, original identity JSON bytes, and original
index/cache bytes, removes
only snapshot copies created by this repair, and removes newly created directories
only when empty. Backups and journals remain available. An interrupted rollback
can be continued with the same rollback command. Keep enough free space for a
complete copy of all planned session directories plus affected indexes/caches
and copied workspace snapshot assets.

## Explicit limits

- Unregistered remote identities, linked or isolated worktree identities,
  unavailable local workspace paths, conflicting identities, duplicates, and destination
  collisions are reported for manual handling. Registered remote sessions stored
  on this machine are supported; the script does not contact the remote host.
- This is an offline local-data utility. It does not contact peers, relay services,
  mobile clients, bots, or detached workers, and never falls back from remote data
  to a controller's local workspace. Run it on the data-owning host for local
  local or remote workspaces controlled from another device, with every writer stopped.
- Symlinks, junctions, other reparse points, and special files in session storage
  are rejected. No existing destination session or differing snapshot is replaced.
- Filesystem permissions/timestamps are copied on a best-effort basis; relative
  paths, file types, sizes, and directory structure are fingerprinted without
  reading large session files. This repairs migration
  anomalies in sessions; it is not a product migration or a general corrupted-data
  recovery tool.

Do not edit the old default assistant's path to a named assistant by guesswork:
when the corresponding assistant no longer exists in the registry, it remains
unresolved and is reported for manual mapping.

## Focused verification

```shell
python scripts/recovery/repair-session-storage.test.py
```

Tests use generated temporary data only, including Chinese workspace names,
legacy assistant ID/path rewrites, local/remote directory collisions, hidden
children, connection-scoped snapshot dependencies,
interrupted writes/renames, resume, rollback, stale plans, and link rejection.
They never read or modify the developer's real OpenBitFun sessions. Configure
`TEMP`/`TMP` externally when a particular temporary drive is required.

## GUI alternative

[OpenBitFun Data Tools](../../src/apps/data-tools/README.md) provides a native
Session repair GUI for the same migration anomalies without requiring Python.
GUI and script plans/journals use independent formats. Both tools share the
product repair lock and must not run concurrently.
