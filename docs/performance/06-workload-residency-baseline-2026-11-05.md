## 资源测量协议

旧协议仅按启动前后 PID 差集捕获 WebKit 候选。新协议在 macOS 测试适配器中单独启动目标，验证其 Darwin responsibility 身份，再动态枚举归属该目标的进程。预演确认主程序和 WebKit/GPU/Networking 的 responsible PID 均为目标程序 PID；原生测试同时运行一个无关进程，确认其被排除。

这解决进程归属，不推导某个 WebContent 对应哪一个页面，也不将多个进程的 RSS 相加称作独占物理内存。启动使用运行时解析的 Darwin SPI，其用法参考 [LLVM LLDB 的启动实现](https://lldb.llvm.org/cpp_reference/PosixSpawnResponsible_8h_source.html)。该适配器仅用于 E2E；接口不可用或归属验证失败时明确报错。

| 指标 | 来源与口径 |
| --- | --- |
| CPU | `proc_pid_rusage` 累计 user/system time，经本机 Mach timebase 转成毫秒，除以单调时钟窗口；100%为一个逻辑核 |
| CPU 校准 | 每次运行前以 `CLOCK_PROCESS_CPUTIME_ID` 对照约100 ms CPU 工作量；首轮100.0010 ms参考值对应100.0103 ms采样值 |
| 内存 | 分别记录 resident size、physical footprint、lifetime peak；`vmmap -summary`在计时窗口外提供分配分类 |
| 后台开销 | package idle wakeups、interrupt wakeups、pageins、磁盘读写累积值 |
| GPU | 归属明确的 GPU 进程 CPU/footprint，以及系统 AGX 观察；应用 GPU busy/独占显存仍未取得 |
| 生命周期 | PID与启动时间共同标识进程；启动/退出进程标记覆盖不完整，不混作完整窗口样本 |
| UI/逻辑资源 | DOM、保留场景、动画、canvas、编辑器、PTY、只读逻辑缓存账本；清理断开的 WebDriver 句柄，不清产品缓存、不强制 GC |

11月6日再次核对GPU工具：本机选中`/Library/Developer/CommandLineTools`，`xcrun --find xctrace`返回不可用；`powermetrics`帮助中提供`--show-process-gpu`，但普通权限的一次调用返回`must be invoked as the superuser`，没有取得采样。以上是工具可用性证据，不是应用GPU时间／显存结果；未以进程CPU或系统AGX替代缺失指标。

正式默认协议：60轮×8个入口，保留1个1,200行编辑器、真实 PTY 和80回合会话；四个180秒资源窗口（首页、待办、恢复首页、关闭后首页），另有600秒窗口隐藏。每5轮记录检查点。窗口前稳定5秒，资源每2秒采样；截图和内存分类检查不进入计时窗口。

### PTY自然退出：僵尸进程及状态不更新

`terminal-exit-diagnostic-4`读取既有startup trace：输入shell退出命令前4次`terminal_write`，输入后6次，额外Enter／Ctrl-J后8次；全部成功，最长2 ms，没有缓存命中。它证明请求经过前端队列和API返回，但PTY writer本身是异步命令队列，仍不能单独证明shell执行。

`terminal-exit-diagnostic-5`进一步通过OS `ps`读到目标shell为`Z / <defunct>`，父PID仍是本轮应用。此前“shell仍存活”的判断应修正为“shell已经退出但未被回收”。对僵尸进程的`sample`尝试失败，未取得调用栈，也未申请更高权限。

源码中`spawn_pty`只在收到主动Shutdown命令时调用`try_wait`并发送Exit；自然退出没有waiter，读线程遇到EOF也不更新状态。因此shell退出后留下僵尸、PTY元数据仍Active，不能获得正确的最终资源基线。修复前再次刷新main（`d6a640fcc`），此文件与本地原实现一致；按terminal／PTY／exit检索开放及草稿PR，并检查返回的#3588、#3751、#3532、#3004文件，均未覆盖该路径。
