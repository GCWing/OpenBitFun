日期：2026-11-05。代码基点：`18eeb95db`。本报告记录本机实测，区分已达标、仍需优化和未覆盖项。

本轮工作于11月6日收尾，综合结论与最终状态见[性能优化收尾报告](08-performance-wrap-up-2026-11-06.md)。本文保留各阶段的原始口径及限制。

**11月6日口径校正：** 已复核保留的P0前后快照，HTML均声明`harmony-bundled`，这是通用Web字体配置；macOS Desktop正式构建选择`apple-system`。本报告的同配置前后对照及几何检查仍保留，但资源和延迟数值不能直接作为macOS默认字体的基线。尤其后续GPU进程增长已指向大字体数据的重复分配，不能归因于logo图层。匹配实际Desktop字体的新基线见下方持续工作负载报告；切换构建配置的差值不计为产品代码优化收益。

后续长驻留、进程归因及重负载工作见[持续工作负载基线](06-workload-residency-baseline-2026-11-05.md)。其操作序列和采样协议独立，不与本报告直接混算收益。

**最新P0结果：** 已统一三组交叉E2E；修正logo坐标后保留合成优化。首页主WebContent CPU中位数 **19.27% → 0.90%（−95.3%）**，RSS **881.0 → 852.2 MiB**；功能、速度预算与48张截图检查通过。详见第11–13节。第1–10节保留首轮历史基线，不和新协议直接混算。

## 1. 第一轮结论

- 已完成主场景 **109 次打开/切换采样**：7 个导航入口各首开 1 次、重入 8 次，20 个设置页各首开/重入 1 次，以及设置容器、项目资源、文件树、编辑器、长会话、终端。前后均使用真实 Desktop/WKWebView、生产前端、相同 native binary 和独立用户目录。
- MiniApp 本地库热切换 P95 **2593 → 65 ms**；无需增加懒加载，根因是本地列表 loading 等待市场请求。
- 打开上述页面后，导航拖拽各次 P95 **64–66 → 23–25 ms**；中间分栏 **70–73 → 19–21 ms**。两类手势优化后最大帧间隔分别为 **67 / 59 ms**，实际位移及松手归位通过。
- 最终主场景 `functionalPassed=true`、`performanceBudgetsPassed=true`、`passed=true`；自动门槛覆盖普通导航热切换和各次拖拽 P95/max，不代表所有资源目标都已闭环。
- 主 WebContent 的拖拽 CPU 时间明显减少，首页空闲段 RSS 结束值 **913.1 → 790.2 MiB**。GPU 候选进程的 RSS/CPU、Host 空闲 CPU 并未全面降低，**不能宣称整个应用内存或 GPU 占用下降相同比例**。
- 保留现有懒加载、空闲预热、页面状态和可见动画；本轮优化集中于不必要的数据等待、隐藏页面布局和尺寸变量的样式传播。

## 3. 人体感受底线与目标

约 0.1 秒接近即时响应，约 1 秒仍能维持操作连贯性；普通切页应显著快于 1 秒。[响应时间阈值](https://www.nngroup.com/articles/response-times-3-important-limits/)。60 Hz 对应约 16.7 ms 帧预算；超过 50 ms 的主线程长任务需要单独定位。[渲染性能](https://web.dev/articles/rendering-performance/)、[长任务](https://web.dev/articles/optimize-long-tasks)。本报告的 RAF 间隔不能直接当作 Long Task API 测量。

| 维度 | 验收底线 | 继续优化目标 | 本轮状态 |
| --- | --- | --- | --- |
| 普通导航反馈 | 热切换根节点可见 P95 ≤100 ms | ≤50 ms | 实测 31–60 ms，底线通过 |
| 普通本地页 | 热切换内容 P95 ≤150 ms；首次 ≤500 ms | 热切换 ≤100 ms | 底线通过；Skills P95 105 ms，仍有余量 |
| 编辑器/历史会话/终端 | 首次 ≤1000 ms，持续可见反馈 | ≤500 ms | 本轮均通过；首开各 n=1 |
| 拖拽 | 各手势 P95 <34 ms、max <100 ms | 接近16.7 ms，>33.33 ms 占比<1% | 主场景底线通过；慢帧约1.6%，进阶目标未全达成 |
| CPU | 相同工作量累计 CPU 不增加；后台无无效持续工作 | 分别降低脚本、样式、布局、原生后台任务 | 主 WebContent 改善；Host/GPU 候选进程需独立归因，不能整体判绿 |
| 内存 | 稳定循环无持续 DOM 增长；空闲资源无无界增长证据 | 降低真实常驻与峰值，同时保留草稿/终端/阅读状态 | 短时稳定；主 WebContent RSS 较低，未证明长期无泄漏 |
| GPU | 不新增持续渲染、合成负担 | 取得可归属 GPU busy / GPU memory 后定量下降 | 当前只有系统计数及进程 CPU/RSS，应用 GPU 利用率目标待补测 |
| 交互体验 | 实际跟手、归位、草稿、阅读位置与编辑器恢复正确 | 保持动画、快捷键、取消和真实刷新语义 | E2E 与聚焦单测通过；不外推未覆盖平台/场景 |

不能通过降低输入采样、隐藏失败、关闭可见动画、取消数据刷新、切页清空状态来满足目标。启动总时长另列观察值，debug host 单次结果不足以给出 release 冷启动 SLA。

独立诊断运行的原生 `sample` 显示，拖拽 WebContent 主线程881个样本中约392落在样式解析、174在布局，约787属于渲染更新调用链（这些调用链有包含关系，不能相加）。据此优先处理CSS传播/隐藏布局，而非只加React memo。采样运行有额外开销，未混入正式基线。

主WebContent空闲平均CPU24.54%→16.30%，但Host6.11%→9.40%、GPU候选2.57%→4.28%。同一native binary仍有异步网络刷新、状态轮询和伴随窗口活动，不足以将其变化归因于某条前端修改；资源目标不能整体标为完成。首页4个产品SVG动画保持运行；独立空闲剖析可见SVG transform/渲染路径，不通过禁用这些动画换取低CPU。

GPU候选RSS在导航窗口的峰值前1258.8、后1308.3 MiB；空闲结束值173.8→218.0 MiB。主WebContent较低的RSS不能抵消或掩盖这一观察，也不能直接推导出GPU显存。RSS包含共享/可回收页，不等于JS堆，逐进程简单相加会失真。

系统AGX Device Utilization在首页空闲段前81–88%、后83–88%。它包含整台机器其他窗口的GPU活动；**不能据此说OpenBitFun GPU占用80%以上，也不能得出本次优化降低了应用GPU利用率**。GPU进程的CPU%同样不等于GPU busy%。本机没有可用的xctrace应用归因数据。

DOM和存活对象：热切换稳定后主导航DOM基线约2665个、主页约2669个，没有随8轮重入继续增长。空闲前后基线3700→3700节点、优化后3793→3709节点；scene hosts均11。优化后Monaco实例1→0，与现有约30秒非活动视图回收一致；再次进入可恢复。逻辑resource-budget账本均169,948 bytes且空闲前后不变，它只计入被该管理器追踪的数据，绝不是应用总内存。

WKWebView不提供本次脚本可读的`performance.memory`，JSON为null；原生资源协议的Resource Timing为空。两项均记为“不可测”，不填0，不用包大小估算JS堆。

## 7. 懒加载是否必要

**建议保留现有按功能的懒加载；当前不建议扩大成所有页面首次点击才加载，也不建议切走即卸载。** 这是结合现有主路径与重功能边界的工程判断，本轮没有用全量eager的A/B证明某一具体内存节省值。

当前链路：Session等主交互路径直接进入主场景bundle；Terminal、Git、Agents、Skills、MiniApps等使用`lazyWithRecovery`；Settings按页面加载。启动后2.5秒串行调度8个场景预热，另有编辑器空闲预热。打开过的scene host保留状态，内容资源有自己的回收策略。这是“模块加载、组件挂载、数据请求、非活动渲染”四个不同问题。

| 观察 | 优化前 | 优化后 | 能得出的结论 |
| --- | --- | --- | --- |
| JS trace interactive shell ready | 613 ms | 616 ms | 本轮未加速主shell启动 |
| JS trace启动遮罩消失 | 1084 ms | 1104 ms | 既有最短展示及过渡保持 |
| 进程启动到驱动观察shell就绪 | 5141 ms | 6098 ms | 包含debug host/驱动观察等，不能与JS trace同起点比较 |
| 7秒预热段scene hosts | 1→1 | 1→1 | 预热代码没有把所有页面都挂载 |
| 7秒预热段Monaco实例 | 0→0 | 0→0 | 预热不等于创建编辑器视图 |
| 预热段主WebContent RSS | 325.7→511.2 MiB | 325.1→423.4 MiB | 非零资源成本，但含并发启动工作/GC，不能全归因于8个预热模块 |
| 预热段主WebContent累计CPU | 0.77 s | 0.77 s | 不是“首开快就没有CPU成本” |

磁盘前端约93.3 MB不代表启动传输了93.3 MB，也不代表常驻93.3 MB。当前未做关闭预热/全量eager的受控A/B，不能宣称懒加载节省具体MB。已测的首次UI进入大多低于150 ms；贸然取消预热会把解析/初始化成本移到用户点击时。

本轮选择：保留现有加载策略；解除无关网络等待；对已经不可见的场景使用`content-visibility:hidden`跳过后代渲染，保留DOM/React状态；阻断不需要继承的私有尺寸变量。该CSS特性用于控制布局/绘制工作，并不卸载模块、释放所有JS状态或停止所有effect。[CSS Containment规范](https://www.w3.org/TR/css-contain-2/)、[content-visibility](https://web.dev/articles/content-visibility?authuser=0)。

后续若优化预热，需要同数据、同机器交替运行“现状/减少预热”各至少5次，分别记录启动到可交互、首点延迟、0–10秒CPU、常驻/峰值内存和后台工作。只有实际首点仍满足人体感受底线且资源稳定下降，才调整预热清单；不把内存下降建立在丢草稿、滚动位置或重建终端上。
