# Relay、账号与远程连接常见问题

[English](FAQ.md) · [运维指南](README.md)

## 需要自己部署服务器吗？

不需要。发布版客户端默认通过官方 Relay 实现同账号设备互控。在宿主与控制端
登录同一个 OpenBitFun 账号，按 Remote Connect 的邀请或设备选择流程连接即可。
宿主需要保持运行且可连接。官方端点为 `https://remote.openbitfun.com/v/1.0.2`，
路径中的版本是服务协议前缀，不代表当前桌面客户端版本。

| 连接方式 | 使用条件 |
| --- | --- |
| 官方 Relay | 两端可联网并登录同一账号；无需部署服务器或配置 Relay 地址 |
| 同一网络 | 桌面宿主启动内置 LAN Relay，控制端能访问该宿主；登录时仍需联网 |
| 私有 Relay | 自行部署服务并构建配套客户端，见[分支部署指南](README.md#for-community-developers-and-forks) |
| SSH / Docker 工作区 | 能访问目标环境；不依赖 Relay 登录 |

桌面端可同时维持官方与局域网连接。「我的设备」、Peer Device Mode、账号同步
以及通过账号设备派发的 Detached Dispatch 仍使用官方账号端点；开启局域网不会
把这些功能迁移到私有服务器。CLI 不提供内置 LAN Relay。聊天机器人使用各自
平台的配置与配对流程。

## 必须使用 GitHub 吗？

新版客户端支持 GitHub 与邮箱验证码登录，具体入口取决于共享身份服务是否启用。
邮箱登录不需要设置密码。这两种方式创建独立账号，即使邮箱相同也不会自动合并。
各设备必须使用相同的登录方式与账号，才能看到同一组设备。

旧客户端或旧服务可能只提供 GitHub 登录。缺少预期入口时，应核对客户端版本与
服务支持情况。本地使用及 SSH / Docker 工作区连接不需要 Relay 账号；模型和
外部服务的凭据另行配置。

邀请只标识 Relay 端点与目标设备，扫码本身不授予访问权。控制端仍需登录，并在
同账号设备目录中找到目标设备。

## 局域网模式能完全离线使用吗？

局域网设备流量留在所选的本地 Relay，但局域网与官方模式登录时都要通过
`auth.openbitfun.com` 验证身份。本地 Relay 不提供离线开户或登录流程。
已有连接仍处于登录状态，也不代表断网后能完成新的登录或凭据续期。

隔离网络中可考虑本地工作或 SSH / Docker，但仍需满足各自的连接与模型运行条件。
仅自建 Relay 不能去掉在线身份依赖；独立部署还需适配身份服务和客户端。
当前发布版没有开箱即用的隔离网络身份模式。

## 服务能看到什么？

设备控制的传输内容采用端到端加密。各设备在本地生成 X25519 私钥，从已认证的
账号目录获取对端公钥，再通过 X25519 与 HKDF-SHA256 派生 AES-GCM 密钥。
Relay 不接收设备私钥。会话历史与工作区文件按需从持有它们的在线宿主读取，
不以 Relay 中的会话备份作为数据源。

Relay 仍会处理账号 ID、设备注册信息、公钥、在线状态与路由元数据；身份服务
负责登录验证。身份服务与已认证的公钥目录仍在信任边界内。因此，内容加密不能
等同于「数据不经过运营服务」，也不能保护已经被攻破的设备。

已发布的 Pages、Page 数据与函数、市场、模型请求及聊天机器人有各自的数据流。
发布 Page 会按所选可见性规则把内容上传到发布服务。不能把设备控制的加密范围
扩展成对 OpenBitFun 全部网络流量的承诺。

## 官方 Relay 免费吗？有什么额度和 SLA？

仓库记录了技术资源限制，但没有发布 Relay 价目表、月度流量额度或服务等级协议
（SLA）。依赖具体费用或可用性条款前，请查阅当期服务公告，或通过
[项目仓库](https://github.com/GCWing/OpenBitFun)向维护者核实。开源许可证不能
代替托管服务的运营条款。

[资源限制表](README.md#public-service-resource-controls)列出了设备、连接、
请求与消息大小等限制。这些是技术限制，不是订阅额度或无限使用承诺；实际部署
与反向代理还可能采用更严格的限制。旧 0.2.x「Beta 免费」描述不能作为永久免费
或当前额度的依据。旧匿名配对、密码开户和部署向导说明，也不适用于当前的账号
连接流程。

## 服务或设备不可用时怎么办？

新登录需要身份服务可用；官方远控需要 Relay 与目标宿主均可连接。宿主离线时，
不能通过该连接读取它的会话历史与文件。控制端断开不会取消已在宿主上运行的
任务，但宿主必须继续运行，等待授权的任务也仍需有人回答。

设备能互相访问时，桌面端的同一网络连接可提供另一条路径，但仍受上述登录条件
约束。它不会自动接管「我的设备」、Peer Device Mode 或账号设备派发。本地工作
与另行配置的 SSH / Docker 访问不走 Relay。恢复连接后先检查已有任务，再决定
是否重新提交。

## 自托管实际需要做什么？

公开模式使用固定官方端点，没有可手填的服务器地址或部署向导。私有 Relay 需要
统一修改客户端端点、构建兼容的 Relay 与手机网页端、配置持久化存储、TLS 和
反向代理，并持续负责备份、升级、监控与容量规划。如果还要自行运营身份服务，
也需配置受支持的登录方式及其回调或邮件发送。购买一台 VPS 并不能完成这些工作，
费用也没有适用于所有部署的固定估算。

请从[分支部署指南](README.md#for-community-developers-and-forks)与
[版本化部署指南](../../../deploy/relay-v1/README.md)开始。只修改服务器环境变量
不会改变已发布客户端的连接地址。
